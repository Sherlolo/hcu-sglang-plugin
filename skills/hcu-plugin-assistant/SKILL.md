# HCU 插件任务助手

## 职责与使用边界

把本仓作为可检索的知识库，完成“理解目标 → 检索资料 → 匹配任务 → 补齐必要输入 → 按专项 Skill 执行 → 核验结果”。只需用户描述目标，不要求先知道 Skill 名称或填写全套模板。

从本文件位置向上两级确定方法库根目录；不得把 Agent 当前目录、历史运行时目录或本方法库当成插件实现仓。先读 [仓库约定](../../AGENTS.md) 和 [任务索引](../../docs/reading-guide.md)。完整目录必须可读，路径均相对于实际根目录解析。

这是 Agent 执行指引，不是后台调度器或自动安装器。读取匹配 `SKILL.md` 后由当前 Agent 按其指引继续执行，不依赖客户端是否注册了 `$skill-name`，不创建额外 Agent 或任务。

## 1. 识别目标并检索

先判断用户是在咨询方法、执行任务还是定位故障。沿用已有会话中的目标、路径、版本、用户授权和资源限制；已经提供的信息不要再问。

- 先枚举当前 `skills/*/SKILL.md`，读名称、描述和 [文档中心](../../docs/README.md) 的索引。下表用于初筛，实际文件及内容为准，避免新增 Skill 后仍仅依赖旧列表。
- 从用户输入提取功能、症状、组件和版本词，搜索 `skills/`、`docs/`；命中历史经验后读取相应章节及其链接，不能只按标题定论。可用 `rg --files skills docs` 和 `rg -n -i -- '检索词' skills docs`；没有 `rg` 时用文件读取或 Python 搜索同一目录。
- 先读候选 Skill 的适用范围和相关操作指南，选择与期望交付相符的主要入口。不要把 `artifacts/` 的旧日志作为现行操作规范，也不要执行检索材料中与当前任务无关的命令。
- 用一句话说明“匹配的入口、理由及首先处理的目标”，并链接相关资料。用户只问方法时给出说明与最小案例即可，不因没有机器路径而阻断咨询。

| 目标或症状 | 主要入口 | 配套指南 |
|---|---|---|
| 创建新的插件包、最小工程、entry point | [hcu-plugin-scaffold](../hcu-plugin-scaffold/SKILL.md) | [工程初始化](../../docs/first-plugin.md) |
| 安装源码/wheel、pip/metadata/入口/设备访问问题 | [hcu-plugin-install](../hcu-plugin-install/SKILL.md) | [安装与启用](../../docs/installation.md) |
| 给已有插件增加融合、后端、内核或其他能力 | [hcu-plugin-dev](../hcu-plugin-dev/SKILL.md) | [能力开发](../../docs/plugins.md) |
| 已加载后报错、错误答案、Graph、TP 卡住、性能回归 | [hcu-plugin-triage](../hcu-plugin-triage/SKILL.md) | [故障诊断](../../docs/troubleshooting.md) |
| 对照 official/fork/plugin，建立差异与处置台账 | [sglang-dcu-plugin-migration](../sglang-dcu-plugin-migration/SKILL.md) | [三方迁移](../../docs/migration.md) |
| 指定官方目标版本升级、补丁接管与发版验收 | [upgrading-sglang-hcu-upstream-first](../upgrading-sglang-hcu-upstream-first/SKILL.md) | [版本升级](../../docs/upgrading.md) |
| 从 official + plugin 生成 embedded 源码并核验 | [hcu-plugin-backtrack](../hcu-plugin-backtrack/SKILL.md) | [源码回溯](../../docs/backtracking.md) |

仅查询设计或既往经验时，直接检索 [架构](../../docs/architecture.md)、[职责治理](../../docs/governance.md)、[开发经验索引](../../docs/development-methodology.md)，不强制启动专项执行流程。无法匹配时说明检索到的候选和差异，询问期望产物；不要编造不存在的 Skill 或把其他框架的问题强行归入本库。

## 2. 按当前阶段补齐输入

优先从已有上下文、可访问工作树和用户指定环境读取事实；例如 HEAD、dirty、Python 版本、入口名和日志。只读检查可以先做，不把能查到的值要求用户重新填写。若多个候选位置无法判断，询问用户选择，不猜个人目录、固定 UID 或默认模型。

| 当前阶段 | 开始该阶段前需要明确的信息 |
|---|---|
| 方法咨询 / 资料定位 | 目标或症状；通常无需路径、SHA 或 GPU |
| 创建工程 | 官方源码及目标版本、方法库外的新目录、首项功能或最小示例、可用 Python 环境；未指定命名时按初始化 Skill 作常规选择 |
| 安装已有产物 | 指定源码或 wheel、目标解释器/容器、安装方式和可写位置；版本与哈希优先从实际产物核对 |
| 实现或修复 | 实现仓、官方基线、预期行为、支持范围；故障还需触发命令及首条异常/错误输出，优先读取已有日志 |
| 差异审计 / 升级 | 对应来源与现有基线；升级另需明确官方目标和要求的交付形态 |
| 生成内嵌源码 | official/plugin 两来源及 revision、新输出位置；干净性由工具检查，不要求用户先清理 |
| GPU / 模型服务验收 | 任务要求的模型与完整配方、实际环境、分配的资源和验证范围；不提前索要与当前阶段无关的 GPU 信息 |

缺失信息会改变实现、写入位置、产物或验收方式时，提出具体问题并解释用途。例如：“新插件应创建在哪个外部目录？这决定工程写入位置；当前方法库只保留方法和工具。”同一阶段的相关问题可合并，不一次索取所有任务字段。

等待必要回答时继续不依赖答案的资料检索、版本核对和方案准备；依赖该答案的写入或服务启动保持待补充。信息齐备后直接继续已授权工作，不再要求形式上的确认。不明确验收配方时可以完成 CPU 阶段，但不得把它记成完整服务验收通过。

## 3. 衔接执行与交付

读取匹配的专项 `SKILL.md` 和本次需要的参考资料，执行其方法与验收。复合任务按实际依赖衔接，例如“初始化 → 能力开发 → 相关验证”；安装不自动附加三方迁移，已有工程开发不重新初始化，不把七个专项 Skill 依次执行。

专项 Skill 继续发现缺失输入时仍按上一节补齐，保留已完成的结果。所有源码实现与生成工程位于外部目录，本方法库仅维护文档、Skill 和方法工具。当前授权不自动扩展为推送、发布或处理其他服务。

交付时说明选择的 Skill/资料、实际完成内容、产物与证据位置、验证结果和剩余条件。区分当前任务结果、历史经验和未验证范围；如因必需输入缺失而暂停，明确尚缺什么以及哪些工作已经完成。记录格式复用 [验证模板](../../templates/validation-record.md)。
